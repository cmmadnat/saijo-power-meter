## Critical Risks Requiring Immediate Attention

### 1. [DATA-002]: Incorrect Comparison Results Logic

**Score: 6 (High Risk)**
**Probability:** Medium (2) - Complex logic with 40+ field comparisons, multiple edge cases
**Impact:** High (3) - Incorrect results affect manufacturing quality decisions; false failures block valid units, false passes ship defects

**Detailed Analysis:**
The field-by-field comparison logic is the core functionality of this story. With 40+ fields to compare (15 indoor, 30+ outdoor), each requiring:
- String to numeric parsing
- Null/empty string handling
- Min/max range validation
- Boolean result string generation

A subtle bug in any branch could have severe consequences:
- **False Negatives (fail → pass)**: Defective units shipped to customers
- **False Positives (pass → fail)**: Valid units rejected, wasted inspection time

**Affected Components:**
- `FunctionTestService.compareNumericField()` utility method
- `FunctionTestService.getIndoorResultAndStandard()` comparison logic
- `FunctionTestService.getOutdoorResultAndStandard()` comparison logic

**Mitigation Strategy:**
1. **Comprehensive Unit Testing**
   - Test comparison utility with boundary values (min, max, just inside, just outside)
   - Test with scientific notation, large/small decimals
   - Test with null, empty string, unparseable values
   - Test with edge cases: min = max, negative values, zero
2. **Integration Testing with Known-Good Data**
   - Create baseline test data sets validated manually
   - Compare automated results against manual validation
   - Use production-like data patterns
3. **Code Review with Focus Areas**
   - Boolean logic correctness (inclusive vs exclusive ranges)
   - Edge case handling completeness
   - Parsing error handling
4. **Property-Based Testing**
   - Consider using property-based testing frameworks
   - Generate thousands of random valid/invalid inputs
   - Verify comparison properties hold (e.g., transitivity, reflexivity)

**Testing Requirements:**
- P0: Unit tests for comparison utility (20+ test cases)
- P0: Integration tests with complete data sets (indoor and outdoor)
- P0: Manual validation against 5-10 real production units
- P1: Property-based tests generating random inputs

**Residual Risk:** Low - After comprehensive testing, confidence in logic will be high

### 2. [DATA-001]: Data Inconsistency Between Test Data and Standards

**Score: 6 (High Risk)**
**Probability:** Medium (2) - Standards recently added in Stories 5.1-5.3; may have gaps
**Impact:** High (3) - Missing/null standard values cause all comparisons to fail, blocking production

**Detailed Analysis:**
Stories 5.1-5.3 added fields to `IndoorUnitStd` and `OutdoorUnitStd` models. If Firestore documents haven't been updated with complete min/max values for all new fields:
- Null standard values → comparison fails → field marked "false"
- Multiple null standards → overall result "Fail" → valid unit rejected

This is especially concerning because:
1. New fields were just added (data migration risk)
2. 40+ fields means high probability of at least one missing value
3. Silent failures possible if logging inadequate

**Affected Components:**
- Firestore `indoor_unit_standards` collection
- Firestore `outdoor_unit_standards` collection
- `IndoorUnitStd` model (Story 5.1 additions)
- `OutdoorUnitStd` model (Story 5.2-5.3 additions)

**Mitigation Strategy:**
1. **Data Validation Script**
   - Create script to scan all standard documents in Firestore
   - Check for null/empty min/max values
   - Report incomplete standards before deployment
2. **Database Migration**
   - Ensure all standards have complete min/max for new fields
   - Populate with reasonable defaults if actual values unavailable
   - Document assumptions for default values
3. **Graceful Degradation Logic**
   - If standard is null/incomplete, return status "INCOMPLETE_STANDARD" instead of hard fail
   - Include warning in response
   - Log occurrences for investigation
4. **Monitoring and Alerting**
   - Add metric for missing standard value rate
   - Alert if rate exceeds threshold (e.g., >5%)
   - Dashboard showing which fields frequently have missing standards

**Testing Requirements:**
- P0: Validate Firestore data completeness before deployment
- P0: Unit test with null/missing standard values (graceful handling)
- P1: Integration test with incomplete standards collection
- P1: Create standard data validation dashboard

**Residual Risk:** Low - After data validation and graceful handling

**Score: 6 (High Risk)**

**Impact:** Medium (2) - Frontend will break temporarily but can be coordinated

**Detailed Analysis:**
Current API response:
```json

  "result": {...},
  "standard": {...}

```

New API response:
```json
{
  "status": "...",
  "result": "...",
  "resultTest": {...},

  "std": {...}
}
```

This is a **hard breaking change**. Frontend code expecting old format will fail with:
- Type errors (expecting object, receiving string for `result`)
- Missing properties (`resultTest` doesn't exist in old model)
- Runtime errors in UI components

**Affected Components:**
- GET `/api/v1/function-test/indoor/result-and-std`
- GET `/api/v1/function-test/outdoor/result-and-std`
- Admin UI function test results components
- Any external integrations calling these endpoints

**Mitigation Strategy:**
1. **API Versioning (Recommended)**
   - Create new v2 endpoints: `/api/v2/function-test/indoor/result-and-std`
   - Keep v1 endpoints with old format for backward compatibility
   - Deprecate v1 over time
   - Frontend migrates at own pace
2. **Feature Flags**
   - Add feature flag `DETAILED_TEST_RESULTS_ENABLED`
   - Return old format when disabled, new format when enabled
   - Enable for testing, disable for production initially
   - Flip flag after frontend deployment
3. **Coordinated Deployment**
   - Schedule deployment window with frontend team
   - Deploy backend first in maintenance window
   - Deploy frontend immediately after
   - Monitor for errors, rollback if needed
4. **Contract Testing**
   - Share OpenAPI/JSON schema with frontend team
   - Frontend writes contract tests against new schema
   - Both teams validate contract before deployment

**Testing Requirements:**
- P0: Document API contract in OpenAPI/Swagger
- P0: Share contract with frontend team for validation
- P0: Integration tests for both v1 and v2 endpoints (if versioning used)

### 5. [TECH-001]: String Parsing Complexity and Error Handling

**Score: 6 (High Risk)**
**Probability:** High (3) - String parsing is inherently error-prone
**Impact:** Medium (2) - Parsing errors cause comparison failures but not system crashes

**Detailed Analysis:**
All field values stored as Strings in models (verified in Stories 5.1-5.3). Each comparison requires:
1. Parse testValue String → Double
2. Parse minStd String → Double
3. Parse maxStd String → Double
4. Compare: min ≤ test ≤ max

With 40+ fields per request, many opportunities for `NumberFormatException`:

**Problematic Input Patterns:**
- Null strings: `null`
- Empty strings: `""`
- Whitespace: `"  "`
- Scientific notation: `"2.5E-3"`
- Locale-specific: `"1.234,56"` (European decimal)
- Infinity: `"Infinity"`, `"-Infinity"`
- Not-a-Number: `"NaN"`
- Overflow: `"1.7976931348623157E309"` (> Double.MAX_VALUE)
- Underflow: `"4.9E-325"` (< Double.MIN_VALUE)
- Mixed formats: `"2.5f"`, `"100L"`
- Trailing units: `"220V"`, `"50Hz"`

**Affected Components:**
- `FunctionTestService.compareNumericField()` utility
- All field comparison loops in indoor/outdoor methods

**Mitigation Strategy:**
1. **Robust Parsing Implementation**
   ```java
   private boolean compareNumericField(String testValue, String minStd, String maxStd) {
       try {
           if (testValue == null || testValue.trim().isEmpty()) return false;
           if (minStd == null || minStd.trim().isEmpty()) return false;
           if (maxStd == null || maxStd.trim().isEmpty()) return false;

           Double test = Double.parseDouble(testValue.trim());
           Double min = Double.parseDouble(minStd.trim());
           Double max = Double.parseDouble(maxStd.trim());

           if (test.isNaN() || test.isInfinite()) return false;
           if (min.isNaN() || min.isInfinite()) return false;
           if (max.isNaN() || max.isInfinite()) return false;

           return test >= min && test <= max;
       } catch (NumberFormatException e) {
           logger.warn("Failed to parse numeric field - test: {}, min: {}, max: {}",
                       testValue, minStd, maxStd, e);
           return false; // Treat parsing errors as comparison failures
       }
   }
   ```

2. **Data Validation at Ingestion**
   - Add validation when test data is saved to Firestore
   - Reject non-numeric values at API boundary
   - Prevent garbage data from entering database

3. **Comprehensive Error Logging**
   - Log all parsing errors with context (field name, test number, values)
   - Track parsing error rate metrics
   - Alert if error rate spikes

4. **Consider Apache Commons Lang**
   - Use `NumberUtils.isParsable()` for validation
   - More robust than try-catch for edge cases

**Testing Requirements:**
- P0: Unit tests with 20+ edge case inputs (see problematic patterns above)
- P0: Integration tests with malformed data in Firestore
- P1: Fuzz testing with randomly generated strings
- P1: Performance testing (parsing 40 fields shouldn't degrade performance)

**Residual Risk:** Low - Robust exception handling mitigates most scenarios
