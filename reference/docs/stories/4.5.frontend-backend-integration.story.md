3. Error handling in service layer propagates to UI components

### Critical Integration Scenarios
The following Gherkin scenarios (from original story) should be implemented as Cypress tests:

```gherkin
Scenario: Function Test data management workflow
  Given the backend APIs are running
  And the frontend application is loaded
  When a user creates a new test standard via the UI
  Then the standard is properly saved to Firestore
  And the UI reflects the new standard in the list
  And the data matches between frontend display and backend storage

Scenario: Suggestion API integration workflow
  Given the Calorie Meter suggestion API is operational
  When a user submits test data through the frontend form
  Then the request is properly formatted and sent to the backend
  And the backend processes the request and returns suggestions
  And the frontend displays the suggestions in a user-friendly format

Scenario: Error handling integration
  Given the backend is temporarily unavailable
  When a user attempts to submit data through the frontend
  Then appropriate error messages are displayed to the user
  And the frontend handles the error gracefully without crashing
  And retry mechanisms work when the backend becomes available
```

### Testing

#### Test Framework Configuration
- **E2E Framework**: Cypress (per docs/architecture/03-3-tech-stack.md:20)
- **Test Location**: `admin-ui/cypress/`
- **Configuration File**: `admin-ui/cypress.config.ts` in frontend root

#### Test Execution Requirements
- Tests run against **real backend services**, NOT mocked endpoints
- Backend must be running on `http://localhost:8080`
- Firestore emulator must be running on port 8089 (per Story 1.5)
- Frontend dev server must be running on `http://localhost:5173` (Vite default)

#### Test Standards (from Story 1.5)
- All E2E tests must be isolated and repeatable
- Test data should be cleaned up after each test run
- Tests should not depend on execution order
- Use Cypress fixtures for test data management
- Follow Cypress best practices for waiting and assertions

#### Coverage Requirements
- All critical user workflows (Function Test CRUD, Calorie Meter suggestions, EMC suggestions)
- All REST API endpoints from Stories 2.2, 2.3, 2.4, 3.2, 3.3
- Error scenarios (4xx, 5xx, network failures)
- Performance validation (NFR4 compliance)

#### Running Tests
```bash
# Start backend (from project root)
./mvnw quarkus:dev

# Start Firestore emulator (separate terminal)
firebase emulators:start --only firestore

# Start frontend dev server (from frontend directory)
npm run dev

# Run Cypress tests (from frontend directory)
npx cypress run                    # Headless mode
npx cypress open                   # Interactive mode
```

#### CI/CD Integration
- Integration tests should run as part of CI/CD pipeline after unit tests pass
- Tests run in headless mode in CI environment
- Test results should be reported to pipeline logs
