**I want** to implement a detailed test result response that includes field-by-field comparison results between test data and standards,

### Source Requirements

**Primary Specification:** `docs/function test spec.pdf` (pages 15-18) defines the exact response structure:

**Response Structure (from PDF spec):**
```json
{
  "status": "",
  "result": "",  // Overall result: "Pass" or "Fail"
  "resultTest": {  // Pass/fail for each field
    "voltage_l1": "true",  // "true" = pass, "false" = fail (as strings)
    "voltage_l2": "true",
    // ... one boolean per testable field
  },
  "test": {  // Actual test values
    "voltage_l1": "220",
    "voltage_l2": "221",
    // ... complete test data object
  },
  "std": {  // Standard values (min/max)
    "item": "item001",
    "voltage1_max": "240",
    "voltage1_min": "210",
    // ... complete standard object
  }
}
```

**Status Field Clarification:**
The PDF specification shows `status` as an empty string with no further explanation. Based on analysis of the response structure and Epic 2 context:
- **Recommended Implementation:** Set `status` to mirror the `result` field value ("Pass" or "Fail")
- **Rationale:** Provides consistency and redundancy for API consumers
- **Alternative Options:**
  - HTTP-style: "OK"/"ERROR"
  - Empty string if frontend doesn't currently use this field
- **Implementation Guidance:** Use `result` value unless frontend team specifies otherwise

### Field Mapping and Comparison Logic

[Source: docs/Function test spec.pdf, pages 15-18]

**Comparison Algorithm:**
For each numeric field:
1. Extract test value from `IndoorUnitData` or `OutdoorUnitData`
2. Extract min and max values from `IndoorUnitStd` or `OutdoorUnitStd`
3. Parse String values to Double (all values are stored as Strings)
4. Check: `min <= testValue <= maxValue`
5. Set field result: `true` if within range, `false` otherwise
6. Handle edge cases: null values, unparseable strings → treat as `false`
